# Simulation: Lone Star Foodservice

A client engagement from first meeting to deployable prototype, built on the real use
cases in this repository. **Lone Star Foodservice is a fictional company.** The people,
the meeting and the data are invented; the code paths and the checks are real.

## Two minutes, if you are reviewing this

1. **[01-meeting/recap.md](01-meeting/recap.md)**: the case in four lines (SBAR), what the
   client wants in three weeks, the decisions log, open questions with owners.
2. **[01-meeting/requirements.md](01-meeting/requirements.md)**: REQ-001 to REQ-010, each
   citing the minute of the [transcript](01-meeting/transcript.md) it came from.
3. **[02-design/](02-design/README.md)**: where it runs, and the three-week roadmap.
4. **[03-decisions/](03-decisions/)**: four ADRs, each naming the requirements it serves.
5. **[report.md](report.md)**: generated by one command; a status and evidence for every REQ.

Then, if you want to see it work: `uv run python -m simulation.run_engagement`.

## The engagement

The client distributes food to about 4,000 restaurants, schools and government kitchens.
Pricing changes take six weeks, two of three COBOL experts retire within two years, and
the data center lease ends in nine months. They asked for three things in three weeks.
Each one is a use case on the same harness.

| Week | Phase | Client asked for | Use case | REQ |
| --- | --- | --- | --- | --- |
| 1 | Assess | A disposition for each of five applications | [Portfolio triage](../usecases/portfolio_triage/README.md) | 001, 002 |
| 2 | Understand | The ORDPRICE rules, written down and tested | [Legacy intake](../README.md) | 003, 004 |
| 3 | Migrate data | Proof CUSTMAST moves without losing a cent | [Data mapping](../usecases/data_mapping/README.md) | 005, 006, 007 |
| All | Platform | A cost cap, a trail, and their own cloud | The harness and [infra/](../infra/README.md) | 008, 009, 010 |

## Run it

```bash
uv run python -m simulation.run_engagement     # fake mode: scripted model replies, no API key
uv run pytest simulation                       # 4 tests, fake mode
```

It prints one line per requirement, writes `report.md`, and leaves one folder per use
case under `runs/`, each with a `trace.jsonl`. Read any of them as a tree:

```bash
uv run python -m harness.telemetry runs/<run_id>
```

In fake mode REQ-001 to REQ-009 report MET and REQ-010 reports READY, NOT APPLIED until
the Terraform has been applied to a project. Fake mode proves the controls; the model
replies are scripted, so the agreement numbers are not evidence of model quality.

## Run it live

One real run of all three use cases costs well under the per-run caps ($0.25, $0.50, $0.25).

1. **Check the model ID and prices.** Model IDs and prices change. Compare
   `claude-sonnet-5-5` and its price with the Anthropic models page, and if they differ,
   edit the three places that name them: `agents/*.md` (front matter), `harness/config.py`
   (`PRICES`), and `MODEL` / `PRICE_PER_MILLION` at the top of each use case.
2. **Set the key in your shell only.** `export ANTHROPIC_API_KEY=...` Never commit it.
3. **Run.** `uv run python -m simulation.run_engagement --live`
4. **Read the report before keeping it.** `git diff simulation/report.md`. A live model may
   disagree with the architect or miss a rule; the report says so, and that is the point.
5. **Set the legacy intake baseline from a live run** (fake runs are refused):
   `uv run python -m evals.check runs/<intake_run_id>/result.json --set-baseline`
6. **Decide what to commit.** The live `report.md` replaces the fake one if you keep it.

## What a person still decides

The agents recommend and prove. People decide: the enterprise architect owns every
disposition, the business owner settles the 2003 volume discount (open question Q1),
security picks the production model route (Q2), and the data owner signs off the mapping
after it reconciles.
